# PC 端振动数据工具

上板后**第一件事**就是跑这里的工具。它负责把串口上的原始字节变成能喂给
NanoEdge AI Studio 的数据集，并在数据看起来不对时**告诉你哪里不对**。

> 全部逻辑都能在**没有硬件**的情况下自测通过 —— 串口只是"另一种字节来源"。
> 所以上板时唯一剩下的变量就只有"接线对不对"。

## 用法

### 0) 看有哪些串口

```
python parse_frames.py --list-ports
```

### 1) 上板第一件事：录一份原始字节

**强烈建议先录后析**。录下来以后改解析逻辑不用重新接线，而且原始数据
是出问题时唯一可信的证据。

```
python parse_frames.py --port COM5 --duration 10 --save-raw raw.bin
python parse_frames.py --port COM5                 # 不指定时长 → 按 Ctrl-C 停
```

### 2) 离线反复分析（不碰硬件）

```
python parse_frames.py --file raw.bin --csv data.csv --plot data.png
python parse_frames.py --file raw.bin --window 1024 --window-out windows\
```

### 3) 完全没有硬件：用假数据把链路走通

```
python parse_frames.py --fake --csv demo.csv --plot demo.png
```

假数据带真实的物理口径（静置 `az ≈ +1 g`、可选的"异常段"幅值跳变），
所以画出来的图和真实振动形状一致 —— 用来先把 PC 端流程和画图审美定下来。

### 4) 硬件刚到手、还在文本档时

```
python parse_frames.py --port COM5 --text --duration 5          # mode 1（200 Hz，g 值）
python parse_frames.py --port COM5 --text --text-raw --duration 5  # mode 0（10 Hz，原始整数）
```

### 5) 实测采样节拍（R6.4 第 ④ 步：**必须实测，不许只用理论值**）

```
python check_rate.py --port COM4
python check_rate.py --port COM4 --expected 1000 --tol 1 --duration 20
```

做法：逐行读串口、给每行打 PC 侧墙钟时间戳，最小二乘拟合 `t(固件拍数) = k · 墙钟秒`，
`k` 就是实测节拍。实测结果：

```
>>> 实测节拍 = 1000.01 Hz   偏差 +0.00 %
>>> 结论：✅ 符合 1000.0 Hz（容差 ±2.0%）
```

**用途**：这是 `TIM2` 的 `PSC/ARR` 与 APB1 定时器时钟算错的**唯一**发现手段 ——
`t` 只证明"中断在跑"，**不证明它跑在 1 kHz**（因为打印是每 100 拍一次，
节拍错 10 倍、`t` 照样每次 +100）。

> ⚠️ **固件必须处于 `APP_OUTPUT_MODE=0`** —— 那是唯一会打印 `t=` 的档。
> ⚠️ **复位后头 3 秒的数据会被丢弃**（`--skip`，默认 3）。这不是矫情：
> USB 转串口芯片的**器件侧 FIFO** 里压着复位前的最后几行，会在复位后与
> 新数据挤进同一个 `read()` chunk、被打上同一个时间戳。
> 实测教训：同一块板子，不丢头几秒量出 `-1.6 Hz` 和 `727 Hz`，丢 3 秒后立刻是 `1000.01 Hz`。
> `ser.reset_input_buffer()` **清不掉器件 FIFO**。
>
> 输出里的 `t 倒退次数` 就是混流哨兵：**>0 先怀疑"新旧数据混流"，别怀疑固件**。

**退出码**：`0` 在容差内 / `1` 超差 / `2` 没采到足够数据（脚本可直接据此 gate）。

### 6) 频谱门禁（R6.4 第 ⑥ 步 / `RISKS.md` R17）

采数据集**之前**的门禁：确认叶频峰**真的可见且明显高于本底**。

```
python parse_frames.py --port COM4 --duration 10 --csv d.csv --plot d.png
python check_blade_peak.py --csv d.csv --plot peak.png
```

判据（逐轴独立，任一轴通过即通过）：

```
本底 = median(幅度谱, f ≥ 5 Hz, 挖掉峰两侧 ±50 Hz)
SNR  = 20·log10(峰幅值 / 本底)     [dB]
通过 = SNR ≥ 12 dB  且  峰幅值 ≥ 0.002 g
```

```
轴   叶频带峰      幅值[g]    本底[g]    SNR[dB]  判定
  ay     361.3 Hz   0.05114   0.00045     41.1   OK
>>> 结论：✅ 通过 —— ay 轴叶频峰 361.3 Hz，SNR 41.1 dB，明显高于本底
```

**退出码**：`0` 通过 / `1` 不通过 / `2` 判不了（数据不足、带宽配置矛盾、读文件失败）。

#### 🔴 谐波自洽校验（叶频带取的可是"带内**最大**幅值"）

搜索带里挑的是**幅值最大**的那个峰，所以**别的谐波会冒充叶频**：叶频 = 3 × 转频，而
`2×` 常常与 `3×` 同量级 ⇒ **只要叶频带下沿低于 `2 × 转频`，`2×` 就会顶替叶频、让门禁假通过**。
（3 V 档之所以没事，纯属巧合：默认带下沿 300 Hz 恰好把 273 Hz 的 `2×` 挡在外面；**降速后这个巧合就没了**。）

所以报告里多了一段「谐波自洽」，并用实测 `1×` 反推期望叶频 `--blade-multiple`（默认 3）× 转频：

```
谐波自洽（叶频应 = 3.00 × 转频）
  az   1× =   68.4 Hz → 期望叶频  205.1 Hz ｜ 带内峰  205.1 Hz，比值 3.00 ✅ 与 3× 一致
  ay   1× =   68.4 Hz → 期望叶频  205.1 Hz ｜ 带内峰  167.0 Hz，比值 2.44 ❌ 与 3× 不符、也不是低次谐波 → 多半是环境峰
  建议叶频带（由 1× 反推，±12%）： 180 230 Hz
```

**只要转频带里有峰，而带内那个峰的比值对不上 `K`，就直接否决**（`❌`）—— 宁可判"不通过"
让人去查搜索带，也不能拿别的谐波冒充叶频放行。两种否决：

| 情况 | 含义 | 怎么办 |
|---|---|---|
| 比值 ≈ 别的整数阶（如 2.00） | 带里那个峰是 **n× 转频谐波** | 把叶频带下沿提到 `2 × 转频` 之上 |
| 比值不是任何低次谐波（如 2.44） | **环境峰**混进了叶频带 | 同上；并先做电机 ON/OFF A-B 对照 |

否决后**工具会把该用的带直接算给你**（`--blade-band` 建议值）。另外若**全谱最强峰不在转频带内**，
它会提示"它很可能才是真正的 1× → 把 `--rot-band` 改成覆盖它"（这条在 `--rot-band` 框歪时救过场：
实测用 `--rot-band 50 100` 配 3 V 数据时，工具从"✅ 通过"翻成"❌ 不通过"并指出真 1× 是 136.7 Hz）。

> ⚠️ **叶频带下沿的经验规则：必须高于 `2 × 转频`。** 反过来说，**把带开宽一点是安全的** ——
> 谐波校验会兜住误入的 `2×`。所以降速档推荐 `--rot-band 40 110 --blade-band 150 330`。
>
> 万一 **`1×` 确实在器件上看不到**（但叶频确实存在），用 `--no-harmonic-guard` 关掉否决权，
> 退回纯阈值判定（此时报告里仍会打"校验不了"）。

> 🔴 **这个工具最容易被忽略的一环是"门限本身可不可信"**，所以报告里有一行
> `噪声上界`：纯噪声在新版数据上能刷到的 SNR 上界。**实测**（`selftest.py` 复现，
> 每档 30 次试验取最大值）：
>
> | 数据 | 段数 | 纯噪声 SNR 最高 |
> |---|---|---|
> | 1.0 s | 1 段 | **11.6 dB** ← 12 dB 门限几乎被噪声够到 |
> | 3.0 s | 4 段 | 6.2 dB |
> | 10 s | 18 段 | 3.2 dB |
>
> 所以**采 1 秒数据是判不出这件事的**（工具会打红字提示"余量不足"并把该采几秒算给你）。
> 机理：分段平均（Welch）把每个谱线的相对起伏压到 ≈`2.8/√K`，段数越多本底越"平"。
>
> ⚠️ **采样率从 CSV 的 `t_s` 列反推**（`1/median(diff)`），不硬编码 1000 ——
> 第 ④ 步实测过 `1000.01 Hz`，拿实测值算频率才不会把峰标错。
>
> ⚠️ **两个频率天花板**：器件加速度带宽 **260 Hz**（R17，`DLPF_CFG=0`）、
> Nyquist = 采样率/2 = **500 Hz**。默认叶频带是 300–660 Hz，**带顶超过 Nyquist**，
> 所以落在 340–500 Hz 的峰**分不出**真实频率是 `f` 还是 `1000 − f` ——
> 实测把 612 Hz 的信号报成 387.7 Hz。判据仍然通过（能量确实在），
> 但**频率位置不能写进结论**，要真值就 PWM 限速把叶频压到 Nyquist 以下再测。

### 7) PWM 扫频：把转速找到「工作点」上（R6.4 第 ⑦ 步）

> 🔴 **先跑 §8 的命令通路验收**（不需要电机、不需要电池），过了再做本节 ——
> 否则「电机不转」时你分不清是「命令没送到」还是「接线 / MOS 有问题」。

**为什么需要它**：MPU6050 加速度计带宽上限只有 **260 Hz**，而 3 V 直驱时
叶频 `3 × 136.7 = 410 Hz` 已经在带宽之外；同时 1 kHz 是固定输出率 ⇒
**Nyquist 恒为 500 Hz，往上没有路**。所以唯一出路是**把转速压下来**：
转频 ≈80 Hz → 叶频 ≈240 Hz，1×/2×/3× 全部落进带宽内，幅值才变可信。

一条命令扫完并直接给结论（省掉"发命令 / 录 / parse_frames / check_blade_peak"四五轮）：

```bash
python pwm_sweep.py --list-ports                     # 插着 CH340 时可能还有 ST-Link 虚拟串口
python pwm_sweep.py --port COM4                      # 默认扫 30/40/50/60/70 %
python pwm_sweep.py --port COM4 --duties 20:90:10 --dwell 5
python pwm_sweep.py --port COM4 --duties 55 --save-dir ./sw55
```

每一档它都做四件事：

1. **平滑升降**占空比（`--ramp-step`，不突跳电流）→ 等 `--settle` 秒转速稳；
2. 采 `--dwell` 秒二进制帧 → **两遍**频谱分析：先用宽转频带测出 1×，
   再用 `blade_band_for(1×, K)` 反推**窄叶频带**重算 ——
   窄带下沿自动高于 2×，从根上排除"2× 冒充叶频"（R6.4.4）；
3. 按**固定顺序**判定：`1× 可不可信` → `叶频在不在 260 Hz 内` → `叶频过不过判据`，
   标成 `OK / !rot / !1x / !bw / !blade`；
4. 收工**自动把占空比归零**，并给出推荐档 + 下一步命令
   （`parse_frames.py` / `check_blade_peak.py`，搜索带已按实测 1× 算好）。

固件前置（缺一不可）：固件必须是 **mode 2**，且已带 PWM 通道
（上电横幅里应有 `PWM: PA6/TIM3_CH1 @20000 Hz, duty=0%` 那一行）；
接线共地 + 电机两端续流二极管 + 电机供电走电池盒 3 V（**不是 5V 排针**）。
**每档摸一下 MOS 温度。**

🔴 `!bw` 与 `OK` 的差别就是这一步的全部意义：叶频超出 260 Hz 时
**频率位置可信、绝对幅值不可信** —— 只有看到 `OK`，才说明手里的是
"位置和幅值都可信"的数据。

#### 🔴 两个必须会判的边界情况

- **一个 1× 都没测到** → 工具**不给任何档位建议**（不会拿"最接近的"糊一个），
  而是列出该查的四件事：固件是不是 mode 2、口选对没有、电机真在转吗、
  传感器有没有和电机刚性固定。
- **各档 1× 离散度 < 3%** → 直接报"**占空比很可能根本没生效**"。
  这是个**能证伪**的判据：3.3 V 栅压下占空比从 30% 走到 70%，转速不可能不动。
  没有这一条，很容易把"命令没送到"读成"电机很稳"。

### 8) PWM 命令通路验收（第 ⑦ 步 ①②③④ · **不需要电机、不需要电池**）

只有两根 USB 线（ST-Link + CH340）时就能跑，验的是「命令能不能真的改到占空比」：

```
python check_pwm_cmd.py --port COM5
```

判据四条：

| 步骤 | 期望 |
|---|---|
| ① 复位横幅 | `PWM: PA6/TIM3_CH1 @20000 Hz, duty=0%` |
| ② 发 `d40` | 回显 `[PWM] duty = 40%` |
| ③ 发 `?` | 回显带 `(PA6/TIM3_CH1 @20 kHz; cmd: dNN, NN = 0..100)` |
| ④ 收工 | 自动发 `d0`，回显 `duty = 0%`（不留残余占空比） |

🔴 **不要手工用串口终端做这四步** —— 它要求两条顺序，做错会得到**假故障**：

1. **先开串口、再复位**：启动横幅只在复位后立刻打印，端口没开时到达的数据在 Windows 上会被丢弃。
2. **同一个串口对象只用一个线程读写**：后台线程读 + 主线程写会让读线程静默死掉，
   现象是「发完命令一个字节都收不到」，**看着像固件挂了，其实是观察手段坏了**（`PLAYBOOK.md` 踩坑 20）。

两条都已固化在 `check_pwm_cmd.py` 里。常见参数：`--duty 60`（换验证用的占空比）、
`--keep-duty`（不收工归零）、`--no-reset`（跳过判据 ①）。

> 退出码：0 = 全过；1 = 有用例失败；2 = 环境 / 参数问题（串口打不开、`--duty` 越界、找不到 STM32CubeProgrammer）。

### 9) LED 目视验收 / 万用表量电压（第 ③ 步 · 只接 `SIG` + `GND`，功率侧全悬空）

接上 `SIG → PA6`、`GND → 任意空 GND` 之后，可以让模块上的指示灯当"验电端点"：

```
python check_pwm_cmd.py --port COM5 --led-test
```

它循环发 `d100 → d40 → d0`（每档 3 秒，默认 3 轮，共约 30 秒），**灯是唯一的判据**：

| 档 | 灯应该 |
|---|---|
| `d100` | 最亮 |
| `d40` | 明显变暗（约四成亮度） |
| `d0` | 灭 |

🔴 顺序刻意做成"**亮 → 变暗 → 灭**"——中间那个 40% 是对照组，用来排除
"灯本来就常亮 / 本来就不亮"这类误判。

参数：`--cycles 5`（多循环几轮）、`--hold 6`（每档停更久，慢慢看）。

**灯不可信时改用「量电压」（更硬）** —— 这是**推荐做法**，因为它无歧义（灯到底挂 `SIG` 还是 `VCC`、
亮度差异看不看得出，都是不确定的）。用 `--set` 把占空比**停住**，再拿万用表慢慢量：

```
python check_pwm_cmd.py --port COM5 --set 100    # 停在 d100
python check_pwm_cmd.py --port COM5 --set 40     # 停在 d40  ← 决定性的一档
python check_pwm_cmd.py --port COM5 --set 0      # 停在 d0
```

量法：万用表**直流电压档**，黑表笔接 `GND`、红表笔接**模块的 `SIG` 针**（或板上同网络的 `PA6` 焊盘）。
20 kHz 会被表积分成平均值 = `3.3 V × 占空比`。`--set` 走完**故意不归零**，方便你有时间读数；
要收工就再 `--set 0` 一次。

🔴🔴 **只有中间档能证明 PWM 存在 —— 别被 3.3 V / 0 V 骗了**：

`main.c` 的 `App_SetDuty()` 用 `CCR = (ARR+1) × pct / 100`（`ARR = 4199`），所以

| 档 | `CCR` | 引脚实际是 | 万用表读数 | 能证明什么 |
|---|---|---|---|---|
| `d0` | 0 | **恒定低** | 0 V | 仅"没被钉高" |
| **`d40`** | 1680 | **20 kHz 方波**（40%） | **≈1.32 V** | ✅ **只可能来自方波 ⇒ 决定性判据** |
| `d100` | **4200 > ARR** | **恒定高**（真 100%） | ≈3.30 V | 仅"没被钉低" |

⇒ **`d100` 读 3.3 V 证明不了任何事**（引脚被钉死在高电平也是 3.3 V）。
要证明"`PA6` 上真有 20 kHz 波形"，量 **`--set 40` → ≈1.3 V**：一个不翻转的引脚**给不出 1.3 V**。

> 🎉 **实测通过（2026-10-13，真机）**：只接 `SIG→PA6` + `GND→GND`（功率侧悬空），`--set 40` 时
> **万用表读 `SIG` 对 `GND` = 1.28 V**（= 3.3 V 的 **38.8%** ≈ 设定的 40%），**同时模块指示灯亮**。
> 两条独立证据同源互印 ⇒ `PA6` 上确有 20 kHz 方波。另：`VCC` 未接而灯仍亮 ⇒ 该模块的灯**确实挂在 `SIG` 通路上**。

🔴 **先确认你看的是哪个板子的灯**（这一步最容易被误判）：

| 板子 | 灯 | 行为 | 含义 |
|---|---|---|---|
| **STM32 板自己** | `D1` | **常亮** | 电源灯，永远亮 |
| **STM32 板自己** | `D2` | **5 Hz 闪** | 心跳：`main.c` L601 每 10 Hz 打印翻转一次 → `g_sensor_ok=1` 的证据 |
| **IRF520 模块** | — | 应随 `dNN` 变亮/变暗 | **这才是第 ③ 步要看的灯** |

⇒ **"一个常亮 + 一个闪"恰好就是 STM32 板自己那两个灯的样子**（`D1` + `D2`），
那是**完全正常**的，但**和 `PA6` 一点关系都没有**。分辨方法：把 `SIG` 线从 `PA6` 拔掉
（功率侧本来就悬空，零风险）—— 拔了还继续闪/亮的，是板子的灯；随之灭掉的，才是模块的灯。

**灯一直不亮**先试两件事：① `SIG` 挪到同一行的 `PA7` 再跑（插错一格零风险）；
② 把模块 `VCC` 接到板上 `3V3`（部分版本的指示灯由 `VCC` 供电，不是 `SIG`）。

### 10) 六姿态静态标定（T3 · 不需要电机、不需要电池）

**要解决什么**：单姿态只能量到「实测 − 真值」这一个差，而它同时含着**零偏 `b`**
（常数偏移）与**增益 `k`**（标度误差）两个未知量 —— 一个方程解不出两个未知数。
把板子**翻转 180°** 再采一次，同一个轴就有两个方程：

```
R₊ = k·(+16384) + b     （该轴朝上）
R₋ = k·(−16384) + b     （该轴朝下）
⇒ b = (R₊+R₋)/2      k = (R₊−R₋)/(2×16384)      修正：a_true = (R_meas − b)/k
```

三个轴各来一遍，共 6 个姿态。**这是本项目唯一不依赖 DRV8833 的硬件活** ——
只要 MPU6050 已上板（R6.4 ①②）就能做。✅ **本项目已于 2026-10-15 跑完并收口（T3）**，
结论见本节末「📌 本项目的实测结果」。

### 12) 串口升级（OTA · `S6`）与坏包拒收（`S7`）

**这是 `ota_send.py` 的活**，与上面 1)–11) 那套"采数据"工具是两回事：上面都在 App 里跑，
这个是**让 Bootloader 从 PC 收一份新固件**。

**前置**（少一个都白跑）：

1. 板上跑的是 **Bootloader**（不是 App）—— 看横幅是不是 `=== stm32-ota-bootloader vX.Y ===`；
2. **CH340** 接好（`TXD→PA10` / `RXD→PA9` / `GND`），串口 115200-8N1；
3. 要发的是 **SlotB 链接版**镜像（`.isr_vector` VMA = `0x08060000`）—— 发错了会在"读完回 CRC32"那步被拦下；
4. App 还在跑的话，**先发 `d0`** 把 PWM 归零（`RUNBOOK` R13.5：Bootloader 跳转前 DeInit 后 `PA6` 会停在最后一次比较电平）。

```bash

# ① 先自己自检（不碰硬件）：3 条固定向量全 PASS 才算工具本身是对的
D:\STM32Projects\pc-venv\Scripts\python.exe tools\ota_send.py --selftest

# ② 只算不发：看长度 / CRC32 / 帧数 / 时间估算（对不上就先别发）

  --bin "D:\STM32Projects\_tmp\app_slotB.bin" --ver 2 --dry-run

# ③ 真升级：脚本会一直喊 'u'，并让 ST-Link 自动复位一次去撞那 2 秒的升级窗口
D:\STM32Projects\pc-venv\Scripts\python.exe tools\ota_send.py \
  --port COM5 --bin "D:\STM32Projects\_tmp\app_slotB.bin" --ver 2 --stlink-reset
```

**跑完会自动判 6 条**（不靠肉眼看）：读完回 CRC32 与声明值一致 / 已置 `update_pending=1` /
复位后走到提交步骤 / `active_slot` 切到 B / 真的跳到 Slot B / App 横幅出现。**全过才退出码 0。**

#### 12.1 坏包拒收（`S7`）：`--corrupt N`

```bash
# 让**设备**先放弃（--retries 12 > 设备侧 BL_OTA_MAX_RETRY=8），才证得到它自己的重传预算
D:\STM32Projects\pc-venv\Scripts\python.exe tools\ota_send.py \
  --bin "D:\STM32Projects\_tmp\app_slotB.bin" --port COM5 --corrupt 0 --retries 12 --stlink-reset
```

**预期（实测 2026-10-16，5/5 判据全过、退出码 0）**：

```
[OTA] frame 0 crc16 FAIL got=0xD754 want=0x7365 -> NAK (expect retransmit)     × 8 次
[OTA] frame 0 gave up after 8 tries -> abort
[BL] slot B ... first=0xFFFFFFFF reset=0xFFFFFFFF -> blank (never programmed)
[BL] slot B became INVALID during the update window -> NOT jumping             ← 不跳（S7 修的）
[BL] NOTE: falling back to slot A because slot B is not bootable
[BL] JUMP -> slot A @0x0800C000 ... entry=0x0800E4C1                           ← 回退到 A
```

`--corrupt` 模式会**换成另一套判据**（"该失败的地方失败了"才算过）：设备回了 `NAK` /
设备自己的重传预算用尽后中止 / 坏帧没被接受 / 没走提交安装 / **没有跳进那个刚被判坏的槽**。
⚠️ 这套判据**在失败退出路径上也会打印**，所以别只看 `returncode`。

🔴 **`--corrupt` 的字节改动必须发生在算完 CRC 之后**（改帧内 payload、CRC 保持旧值）。
先改 payload 再 `build_frame()` 的话，CRC 会照改后的数据重算 ⇒ 帧**自洽** ⇒ 设备**正确地**收下，
测出来的根本不是帧层拒收（2026-10-16 首跑就踩了这个坑）。

🔴 **残余（留给固件侧 `S8`）**：`--corrupt 20`（写到一半才失败）时，槽里"向量表完好、内容半截"，
`BL_ImageCheck()` 只看头 8 字节 ⇒ 仍判 `valid` ⇒ **仍会 `JUMP -> slot B`**，之后板子**串口一个字都没有**。
此时那条判据会 **FAIL**（4 PASS / 1 FAIL）—— 这是**预期**，见 `MVP/docs/context/RUNBOOK.md` **R13.12** 与 `RISKS` **R22**。

> 🔎 顺带一个反例教科书：`--corrupt 0` 之后 Slot B 是**空白**的，`active_slot` 仍是 `B` ⇒
> 下次上电会 `falling back to slot A`。想恢复成"从 B 起"，**再跑一次不带 `--corrupt` 的正常升级**即可。

**三个必须知道的坑**：

| 现象 | 原因 / 对策 |
|---|---|
| 一直是 `🔴 没能进入升级模式` | `u` **只在上电后 2 秒内喊得到**（只要槽里有合法镜像，Bootloader 几毫秒就跳走了）。要么加 `--stlink-reset`，要么手按 RESET —— **单发一次 `u` 再傻等是错的**，脚本因此是"一直喊" |
| `🔴 第 N 帧连发 5 次都被拒` | 帧对不上（CRC16 或 seq）。**这就是 `S7` 要验的行为** —— 故意用 `--corrupt N` 复现（见 §12.1），此时设备应当拒绝且**不改元数据**、下次上电仍跑旧版本 |
"
    "| `[OTA] not a start line: "us42788,…"` | 喊 `u` 的轮询与握手行**撞车**（进去那一刻还有一句 `u\n` 在路上，`\n` 被 UART 溢出吃掉 ⇒ 两行粘连），而设备**只等 1 s 就 abort**。已加三道防线：见到 `[OTA] send:` 后 `drain 0.5 s` / 握手行**前置 `\n`** / 6 s 未接受则**重发 ≤3 次** |
| 发了 SlotA 版镜像 | 设备会在 `[OTA] readback crc32 ... MISMATCH` 处拒收（链接基址不同，跳过去必崩，靠校验拦住） |

> 🔴 **升级完 `active_slot` 就变成 B 了**，而且**没有命令能改回 A**（`m` 只会重写当前元数据）。
> 回退路径见 `RUNBOOK.md` **R13.11** 末尾（ST-Link 烧回 / 等 `S8` 的回滚）。
> ⚠️ 已知局限：目标槽固定 Slot B ⇒ 一旦 `active_slot=B`，**中途失败**的升级会污染正在运行的槽。
> 🔴 **"靠回退到另一槽兜底"只对了一半**（`S7` 实测更正）：只有目标槽**真的不可启动**才会回退；
> "写了一半但向量表完好"的槽仍会被跳进去（板子静默）⇒ 见 `RUNBOOK.md` **R13.10.6 / R13.12**、`RISKS` **R22**。

## 帧格式（二进制档，198 字节，小端）

```
偏移    长度    内容
0       2       同步头 0xAA 0x55
2       2       帧序号 uint16（掉帧一眼看出）
4       1       点数 uint8（= SAMPLES_PER_FRAME，默认 32）
5       n*6     数据：每点 ax, ay, az 各 int16，**按点交错** ax0 ay0 az0 ax1 ...
5+n*6   1       校验和 = 前面所有字节之和 & 0xFF
```

`n=32` 时整帧 = 5 + 192 + 1 = **198 字节**，@1 kHz ≈ **6.2 KB/s**
（115200-8N1 的上限约 11.5 KB/s，留了一倍余量）。

**唯一权威是固件的 `Core/Src/main.c`**（`USER CODE BEGIN PV` 里的 `FRAME_*` 宏）。
改固件帧格式时，`vibframe.py` 要同步改 —— 三方不一致是最难查的一类 bug：
**数据能收到，但每个数都是错的。**

## ⚠️ 两个「帧」不是一回事（最容易搞混）

| | 是什么 | 数值 | 在哪 |
|---|---|---|---|
| **传输帧** | 串口分包单位 | `SAMPLES_PER_FRAME = 32` 点 / 198 字节 | 固件 `main.c` |
| **分析窗口** | 送进 AI 的量 | 计划书 1024 点（1024 @1 kHz = 1.024 s） | PC 端 `--window 1024` |

本工具的职责就是：**把 32 点的小包重组成连续 1 kHz 序列，再切 1024 点窗口**。
**不要为了对齐 1024 去改固件的传输帧长。**

## 三档输出模式（固件侧，`APP_OUTPUT_MODE`）

| 档 | 输出 | 速率 | 带宽 | 用途 |
|---|---|---|---|---|
| `0` | 调试文本，打**原始整数** | 10 Hz | 极小 | 验接线、看数值对不对 |
| `1` | 文本波形 `%.3f` g | 200 Hz | ≈4.4 KB/s | 人眼看波形、调接线 |
| `2` | **二进制帧** | 1 kHz | ≈6.2 KB/s | 采数据集（默认档） |

档位是**编译期**开关（不是运行期）：1 kHz 二进制流和人可读文字混在同一串口后，
PC 端无法可靠解析。用 `--text` 对应档 0/1，不加则对应档 2。

## 怎么看健康度

跑完会打印一行统计，**先看它再看波形**：

```
帧 93 / 采样点 2976 | 校验错 0 | 重同步丢弃 0 字节 | 序号断档 0 次(丢帧约 0) | 尾部残留 0 字节
```

| 现象 | 含义与对策 |
|---|---|
| `重同步丢弃` 只有开头几十~几百字节 | ✅ 正常 —— 那是开机横幅文字 |
| `重同步丢弃` 持续增长 | ❌ 波特率不对，或 `APP_OUTPUT_MODE` 与解析方式不匹配 |
| `校验错 > 0` | ❌ 串口有噪声 / 接线接触不良 / 波特率偏差 |
| `序号断档 > 0` | ❌ PC 端读太慢导致丢点 —— 降采样率或提高波特率 |
| `az 均值` 明显偏离 1 g | ❌ 芯片没贴平，或 LSB 档位/换算写错 |

> `--text-raw`（mode 0）**只有 10 Hz**，而振动主频上百 Hz，会发生**混叠**，
> 所以那时的 `az` 均值**不能**当"静置口径"用。要验 `az ≈ +1 g` 请**停机采样**，
> 或改用 mode 1。

## 输出文件

* **`--csv`** → `t_s,ax_g,ay_g,az_g`（`--lsb` 时追加 `ax_lsb,ay_lsb,az_lsb`）
* **`--window-out`** → `win_0000.csv`, `win_0001.csv`, ... + `manifest.txt`
  （记录源、窗口长度、步长、列名、每个窗口的起始点号）
* **`--plot`** → 4 联图：三轴时域 + `az` 频谱（频谱上标出峰值 = **叶频**），
  切窗口时还会画窗口分界线

## 上板排查顺序（一个点都没解出来时）

1. **接线**：TX/RX 是否交叉、GND 是否共地
2. **端口**：`--list-ports` 确认选对了
3. **波特率**：是否 115200
4. **模式**：固件 `APP_OUTPUT_MODE` 与解析方式是否一致（二进制用默认，文本加 `--text`）
