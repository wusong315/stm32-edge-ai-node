> **中文** · 基于 STM32F407 的边缘 AI 振动故障诊断节点 —— 1 kHz 采样 → 片上 AI 推理 → A/B 双区 OTA → MQTT 上云
>
> **English** · An edge-AI vibration fault-detection node on STM32F407 — 1 kHz IMU sampling, on-device NanoEdge AI inference, A/B dual-slot OTA and MQTT cloud reporting.

✅ **MVP 已闭环（2026-10-26）**：1 kHz 采样 → 片上 AI 推理 → 本地判决 → A/B 双槽 OTA → MQTT 上云，**五段全部真机跑通**。
关键数字：采样 **999.94–1000.01 Hz**（433 s 零丢拍）· 推理 **≈170 µs**（占周期 17.6%）· 模型 **9.2 KB Flash / 11.9 KB RAM** ·

## 这是什么

把「电机振动是否异常」的判断**放在设备本地完成**，而不是把原始数据传到云端再算。

工业现场的泵、风机、传送带需要早期故障预警，但往往**没有稳定网络**，也不适合把 1 kHz 的振动原始数据持续上传。本项目的做法是：

1. **本地采集** —— MPU6050（I²C）以 **1 kHz** 采三轴加速度
2. **本地推理** —— NanoEdge AI 生成的模型**直接跑在 MCU 上**（Cortex-M4F @ 168 MHz），输出异常分数
3. **本地决策** —— 异常时点亮 LED 并上报；**断网也能独立工作**
4. **按需上云** —— 联网时只上传**结论与少量特征**，不传原始数据
5. **可升级** —— A/B 双区 OTA：坏包拒收、砖镜像自动回滚、断电不变砖（**升级由上位机经串口发起，不是云端推送**）
6. **结论上云** —— MQTT 3.1.1 上报异常结论，等平台回执（QoS 1）确认；断线自动重连，**重连期间不丢采样**

以下均为**真机实测**数字（非估算、非引用文档）。

| MCU 型号 | **STM32F407VGT6，1 MB Flash** | 寄存器级复核 `FLASH_SIZE`@`0x1FFF7A22` = `FFFF0400` → 低 16 位 `0x0400` = 1024 KB（**原理图标称 `VET6`(512K) 系印错**） |

| 加速度量程 | 两姿态 `\|a\|` = **16 641（+1.57 %）/ 16 601（+1.33 %）** | 任意姿态皆 ≈16384（±1 g）；翻转 180° 后主分量符号翻转 |

## 片上 AI 与故障判别（真机实测）

模型由自采数据集在 NanoEdge AI Studio 训练（异常检测路线，`learn` 只需正常态数据），**整对替换 `NanoEdgeAI.h` + `libneai.a` 即可，应用代码零改动**。

| 项 | 实测结果 | 判据 / 意义 |
|---|---|---|
| 数据集 | **6 段 / 359 328 点 / 2805 个 128 点三轴窗口**；校验错 / 序号断档 / 丢帧 **计数全 0** | 采样链路可信，才有资格谈模型 |
| 模型体积 | Flash **9.2 KB** / RAM **11.9 KB**（另有 1.6 KB 运行时缓冲） | 单模型占片上 Flash 不到 1 % |
| 推理耗时 | **p50 169.6 µs / max 176.2 µs**（DWT 周期计数，226 帧统计） | 占 1 ms 业务周期的 **17.6 %**，余量足够 |
| 一致性 | 推理错误计数 `err = 0`；相似度稳定输出 | 不崩、不抖 |
| 检出率（阈值 `sim<90`，**逐窗**） | 不平衡 **97.0 %** / 碰擦 **40.1 %** / 外部冲击 **13.6 %** | 同工况误报 **0–2.9 %** |
| 电路级交叉验证 | 同一批数据用 NanoEdge 官方模拟器重算，量级一致（92.3 % / 54.7 %） | 两侧独立实现，结论不依赖单一工具 |

> 🔴 **报数口径**：这是「**检出率 + 误报率**」，不是"准确率"（准确率要含真阴/真阳，本项目没测）。
> 且必须带三个限定：**人为故障**（不是真实轴承失效）、**带量级**（轻配重仅 6.6 %、重配重 97.0 %）、**误报给区间**不是单点。
> 另：模型判的是**频率结构**而非幅值 —— 原始信号 ×0.02 或 ×8，判定结果不变。

## OTA：A/B 双槽 + 自动回滚（真机闭环）

手写 Bootloader（`bootloader/`，独立工程，**32 KB @ `0x08000000`**），App 分 A/B 两槽：

| 场景 | 实测结果 |
|---|---|
| 正常升级 | **8/8 判据全过**：42 帧 → 读回 CRC32 一致 → `active_slot A → B` → 跳转地址与离线 `objdump` 逐字一致 |
| 坏包（逐帧 CRC 错） | **7/7 判据全过**：逐帧 `NAK` 重传 → 用尽即中止 → **不置升级标志、不提交** → 回退原槽 |
| 砖镜像（镜像级 CRC32 不匹配） | **3/3 自动回滚**：`trial 1/3 → 2/3 → 3/3` → `ROLLBACK B → A`，**全程零人工干预** |
| 升级耗时 | 42 788 B / **4.1 s** / 10.2 KB·s⁻¹（停等协议，串口 115200） |

> 🔴 **三条踩过的坑**：① **没有上电窗口就没有升级入口**（槽一合法就几毫秒跳走，PC 插不进来）⇒ 保留 2 s 窗口；
> ② **收数据期间一个字节都不许打印**（F4 擦/写期间 CPU 取不了指，而 UART RX 寄存器只有 1 字节）⇒ 必须停等；
> ③ **跳转前必须 `__set_PRIMASK(0)`** —— 参考工程跳完带着 `PRIMASK=1` 没事（它不用中断），本工程 App 靠 SysTick + TIM2 ⇒ 会卡死在第一个 `HAL_Delay()`。
> ⚠️ **已知局限**：App 不会自动确认 ⇒ **每次正常升级后要发一个 `k`**，否则复位 3 次就自动回滚（这是刻意保留的保守策略）。

## 上云：ESP8266 + 手写 MQTT（真机闭环）

不走 SDK、不引第三方库：ESP8266 只当"网线"（`CIPMODE=1` 透传），**MQTT 3.1.1 报文由 C 逐字段自拼**，HMAC-SHA256 也是纯 C 实现（2.6 KB，零 `malloc`）。

| 项 | 实测结果 |
|---|---|
| 上报与回执 | **PUBACK 与 PUBLISH 逐条 1:1 —— 72/72**（QoS 1） |
| 报文正确性 | 与独立实现的 Python 版本**逐字节对拍 11 项全过** |
| 断线自愈 | 判据 = 字节流解析失败 或 下行静默 100 s ⇒ 重连 **12–14 s**，**重连期间 1 kHz 采样零丢失** |
| 鉴权 | 华为云 IoTDA，`sig_type=0`（不校验时间戳）⇒ 无需 SNTP/RTC |

> 🔴 **四个"不报错但结果全错"的坑**（这是本段最值钱的部分）：
> ① **轮询收包会丢字节** —— 115200 下 87 µs/字节，撞上 170 µs 的推理 ⇒ PUBACK 4 字节丢一个就认不出。改 **1 字节中断 + 256 B 环形缓冲**；
> 但**不能用 `HAL_UART_Receive_IT`**（它会抢 `HAL_UART_Transmit` 持有的锁 ⇒ 拿 `HAL_BUSY` 后不再置位 RXNEIE ⇒ 表现为"AT 无应答"）。
> ② **半包被丢会让整条字节流错位**（`40 02` / `00 01` 分两次到达）⇒ 跨调用暂存区，按「类型 + 剩余长度」切定长报文。
> ③ **MCU 复位了、ESP8266 没有** ⇒ 模块还留在透传里、回 `busy p...`。**把原本跑通的旧固件回刷报同一句错误**，才是决定性反证 ⇒ 新增 `+++` 逃逸，且要**等"真正的静默"**再发。
> ④ **一开始根本没有重连** ⇒ 掉线即永久失联。改为非阻塞状态机（每拍推进一步），不阻塞 1 kHz 采样。

> ⚠️ **带宽问题的最终结论**：初期工况叶频 **410.2 Hz** 确实超出 MPU6050 加速度计 **260 Hz** 上限（该峰频率可信、幅值不可信）。
> 但**换到最终工况后主振动降到 149 Hz，已在带宽内** ⇒ **不需要为带宽而降速**，`R17` 风险关闭。
> PWM 通道仍保留（`PA6` / 20 kHz），用途从"限速"变为"**调速造故障**"与"扫频自检"。

## 硬件

| 部件 | 型号 | 用途 |
|---|---|---|
| 主控 | STM32F407VGT6（LQFP100，**1 MB Flash**） | 采样 + 推理 + 控制 |
| 传感器 | MPU6050（I²C） | 三轴加速度 / 陀螺仪 |
| 通信 | ESP8266（D1 mini，AT 透传） | MQTT 上云 |
| 振动源 | 130 直流电机 + **DRV8833 双 H 桥** | 模拟正常 / 异常工况 |
| 供电 | 独立电池组（2×AA 串联 ≈3 V，与主控隔离） | 避免电机干扰主控 |

> 🔧 **为什么用 DRV8833 而不是 MOSFET**：原计划的 `IRF520` 方案有两个硬伤 —— ① `Vgs(th)` = 2–4 V，**3.3 V 栅压下只部分导通**（掉约 1 V 且发热）；
> ② 感性负载断电反峰会加在漏源之间（实测反峰可达数十至数百伏，远超其 `Vds` 额定），**必须外置续流二极管**才安全。
> DRV8833 是带体二极管的双 H 桥，**无需外置续流二极管**，且固件侧一行不用改（仍是单路 PWM + 方向脚）。

## 时钟与关键配置

| 项 | 值 |
|---|---|
| HSE | 8 MHz |
| PLL | M = 8 / N = 336 / P = 2 |
| SYSCLK = HCLK | **168 MHz** |
| APB1 / APB2 | 42 MHz / 84 MHz |
| FLASH_LATENCY | 5 WS |

| 外设 | 引脚 | 参数 |
|---|---|---|
| I2C1 | PB6 = SCL / PB7 = SDA | Fast Mode, 400 kHz |
| USART1 | PA9 = TX / PA10 = RX | 115200, 8-N-1（调试 + PC 工具） |
| **USART3** | **PB10 = TX / PB11 = RX** | 115200, 8-N-1（**接 ESP8266**，NVIC 抢占优先级 = 1，**1 字节中断 + 256 B 环形缓冲**） |
| TIM2 | 内部时钟 + NVIC 中断 | `PSC = 83` / `ARR = 999` → **1 kHz**（抢占优先级 = 0） |
| **TIM3_CH1** | **PA6** | `PSC = 0` / `ARR = 4199` → **20.0 kHz PWM**（调速造正常/异常工况） |
| GPIO | PA1（User Label: `LED`） | 推挽输出，低电平点亮 |

> ⚠️ **TIM2 分频陷阱**：F407 在 **APB1 预分频 ≠ 1** 时，**定时器时钟 = 2 × PCLK1 = 84 MHz**（不是 42 MHz）。
> 按 84 MHz 计算才得到正确的 1 kHz；若误用 42 MHz 会得到 500 Hz，采样率直接差一半。TIM3 同理。

> ⚠️ **关于 `NanoEdgeAI.h` + `libneai.a`**：这一对文件是**成对产物**，必须来自同一次 NanoEdge AI Studio 导出。
> 仓库里装的是**自采数据集训练出的真库**（`NEAI_ID = 6ad5fc07…`，3 轴 × 128 点）。
> 历史上曾用 ST 官方 HTS221 例程的库作**占位素材**（`AXIS_NUMBER = 1` / `DATA_INPUT_USER = 16`）来先打通链接链路；
> 换库时只做了"整对替换"，**应用代码零改动** —— 因为所有缓冲尺寸都取自库宏。
> 🔴 **防呆设计**：`NEAI_AppInit()` 一上电把 `NEAI_ID` 打到串口 —— **换库后 ID 必须变，没变就是没换成功**。
> 这类"怎么证明你确实换了"的机制，比模型本身更能说明工程习惯。

> 🔴 **训练/推理口径必须逐元素一致**：`REMOVE_DC`（去直流）、`AXIS_MAJOR`（轴优先布局）、窗口长度三项，
> 训练脚本与固件**任何一项不一致，相似度会恒为 0**，而编译、链接、初始化全都正常 —— 是典型的静默失效。
> 本工程用编译期开关把这三项锁死，并在 `to_neai_csv` 导出时默认对齐。

## 输出模式（编译期开关 `APP_OUTPUT_MODE`）

固件用**一个编译期宏**切换四种工作模式 —— 因为 1 kHz 的二进制流与人可读文字**不能共存**（混流后 PC 端无法解析）：

| 档 | 模式 | 采样 | 串口输出 | 用途 |
|---|---|---|---|---|
| **0** | 调试文本 | 10 Hz | 原始整数 | **上板第一件事**：验接线（静置时 `az ≈ +16384` = 1 g） |
| 1 | 文本波形 | 200 Hz | `%.3f` g 值 | 画波形、肉眼判断 |
| 2 | 二进制帧 | **1 kHz** | 198 B/帧 | **采数据集**（原始 int16，精度无损） |
| 3 | **在线推理** | **1 kHz** | 相似度 + 推理耗时 | **最终形态**：数据直接喂片上模型，不传原始数据 |

> 带宽账：115200-8N1 ≈ 11.5 KB/s；3 轴 @1 kHz 文本需 ≈24 KB/s **跑不动** → 全速只能走二进制帧（≈6.2 KB/s）。
> 主循环每次只往串口写 4 字节（≈0.35 ms）+ 一次 I2C 读（≈0.2 ms）< 1 ms 采样周期 → 采样节拍不会被串口拖垮。

## PWM 调速（造工况用）

**动机**：初期工况叶频 410.2 Hz 超出 MPU6050 加速度计 **260 Hz** 带宽上限（`DLPF_CFG = 0` 已是器件最高档），
当时的想法是"**把转速降下来**再采数据集"。**实测换工作点后主振动落到 149 Hz，已在带宽内** ⇒ 该约束自动解除。
PWM 通道保留下来，用途变成**调节转速以制造正常/异常工况**（以及扫频自检）。

- `PA6` = `TIM3_CH1`，`PSC = 0` / `ARR = 4199` → **20.0 kHz** 载波（远高于可听范围，电机不会啸叫）
- **上电占空比固定为 0**，且掉电不保持 —— 上电即安全，不会突然全速转
- 命令走**已接好的 CH340（USART1 / PA10，无需额外接线）**：`dNN` 设占空比（0–100）、`?` 查状态
- ⚠️ **`d0` 与 `d100` 是直流电平**（`CCR = 0` 与 `CCR > ARR`），**证明不了方波存在**；只有**中间档**（如 `d40`）才有意义
- ⚠️ mode 2（二进制帧）下**不回应命令**，以免文本搅乱帧同步
- 🔴 **升级/断电前必须发 `d0`**，否则电机会一直转（OTA 跳转前的 DeInit 清单里含 TIM3）

> 第 ③ 步的电气验证（`d40` → 1.28 V）正是为此设计的"能证伪"判据。

## 本地判决的三条工程约束

模型输出的是 0–100 的相似度，"拿 90 一卡"在实机上会出三个问题，逐条解决：

| 问题 | 现象 | 对策 |
|---|---|---|
| **抖动带** | 正常工况相似度在 82–100 之间来回抖，单门槛落在抖动带正中央 ⇒ 60 s 发出 **75 条**上报（演示杀手） | **迟滞 90/95** + **最小间隔 5 s** ⇒ 降到 13 条/90 s |
| **停机段属 OOD** | 电机停了，模型没见过"静止"，阈值 90 下有 **14.9 %** 的窗被判异常（误报） | **停机不判**：逐窗三轴**交流** RMS < **0.013 g** 一律不判异常（实测停机 max 0.0091 / 额定 min 0.0194，分离度 2.2×） |
| **单窗翻转太敏感** | 瞬态抖动就翻转一次 | **判定去抖**：连续 N 窗才翻状态（N=4） |

> ⚠️ **去抖 N=4 的代价**（必须主动交代）：外部冲击是瞬态，凑不满连续 4 窗 ⇒ **模型能看出 13.6 % 的窗，但固件不会因此告警**。
> 重不平衡（0.1 s 内触发）与碰擦（1.4 s）不受影响。若把 N 调到 2 则冲击可报，但要 17.9 s 才出第一次。

## I²C 总线自愈

MPU6050 在**感性负载开关的瞬间**（电机启停）可能被拉低总线，导致 I²C 挂死。

固件内置 `App_I2cBusRecover()`：在 SCL 上打一串脉冲，把从机**踢回 idle 状态**，随后重新初始化并复检 `WHO_AM_I`。
配合 `App_I2cDiag()` 打印诊断，实测表现为串口走完 `[WAIT] → [DIAG] → [OK]`，**全程无需人工复位**
—— 这也定位出此前"传感器掉线"的真因是**固件锁死**，而不是接线问题。

> 🔴 另有一个隐藏杀手：HAL 的 `I2C_TIMEOUT_BUSY_FLAG` 默认 25 ms，**一次 I2C 失败会卡几百 ms**（超过 1 ms 采样周期，直接丢点）。
> 对策是自己轮询 BUSY 标志约 50 µs，失败即走总线恢复，不交给 HAL 死等。

## 资源占用（实测）

用 STM32CubeIDE 自带工具链（`arm-none-eabi-gcc 14.3.rel1`）命令行构建，`arm-none-eabi-size` 真值：

| 构建 | Flash（`text + data`） | RAM（`data + bss`） | 说明 |
|---|---|---|---|
| **App（mode 3 + 上云，当前形态）** | **76 332 B ≈ 74.5 KB** | **18 192 B ≈ 17.8 KB** | 占 Slot A（336 KB）的 **22.2 %**，RAM 占 128 KB 的 **13.9 %** |
| **Bootloader** | **32 344 B ≈ 31.6 KB** | **3 152 B ≈ 3.1 KB** | 占 32 KB 预算的 **98.7 %** —— ⚠️ **只剩 424 B**，再动代码得先上 `-Os` |
| mode 2（采数据集，无 AI/云端） | ≈ 42.7 KB | ≈ 4.3 KB | 早期形态，历史值 |

> ⚠️ App 那行是 **`-O0` Debug 构建**的实测值（`2026-10-27` 重新编译）。发布版开 `-Os` 会明显更小，但**本项目没有单独统计 Release 体积** —— 没测过的事不编数。
- 四档 `APP_OUTPUT_MODE` = 0/1/2/3 全部**编译 0 error / 0 warning**
- App 体积里较大的一块是**浮点 `printf`**（`-u _printf_float`）≈ **10.5 KB** Flash
- NanoEdge 真库占 **9.2 KB** Flash / **11.9 KB** RAM
## 构建与烧录

1. 用 **STM32CubeMX** 打开 `stm32-edge-ai-node.ioc` —— 需要改外设/时钟配置时从这里改
2. 用 **STM32CubeIDE** 导入：`File → Open Projects from File System…` → 选本工程目录
3. `Project → Build All` 编译 → 通过 **ST-Link** 烧录
4. **日常升级走 OTA**（`tools/ota_send.py`，CH340 + USART1），ST-Link 只在救砖时用

> ⚠️ **工程路径必须为纯英文** —— CubeMX / CubeIDE / GCC / OpenOCD 对含非 ASCII 字符的路径支持不佳。

**不开 IDE 也能验证编译**：本工程可用 CubeIDE 自带工具链直接命令行构建并打印 Flash/RAM 占用
（脚本见本地技能 `stm32-cubeide-cli-build`），便于在无硬件、无 IDE 的场合确认改动是否真的能编过。

> 🔴 **踩过的坑**：`Debug/` 下的 `subdir.mk` 与 `objects.list` 是**生成物**。新增源文件后如果用命令行编译，
> 会链接出 `undefined reference`（清单里没有新目标文件），而 IDE 里点 Build 就正常 —— 容易误判成"代码写错"。
> 更隐蔽的一种：`.cproject` 的档位改了、但槽位清单没重生成 ⇒ **编出来的镜像档位是错的，且不报错**。

## 已知局限

- **云端只做了上行，没有下发** —— OTA 升级走串口本地上位机（`ota_send.py`），**不是服务器推送**；云端命令下发未实现
- **低功耗未做** —— 待机电流与续航没有实测（手上没有 µA 级电流表，万用表读数无意义）
- **int8 量化对照未做** —— 当前库全部 `_f32`、零 int8/定点符号 ⇒ 不存在"量化前"，无从做前后对比（要这个数只能换工具链重训）
- **去抖 N=4 对瞬态不告警** —— 见「本地判决的三条工程约束」末段
- **Bootloader 预算只剩 424 B** —— 再改 Bootloader 代码前必须先上 `-Os`
- **工作点会漂** —— 电池电压下降会让相似度分布整体偏移（`<90` 占比从 0.8 % 漂到 10.7 %）⇒ 验收/演示要用新电池
